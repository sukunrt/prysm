Gossipsub and fork choice

This document shows how a gossip message becomes a fork choice weight in Prysm. It shows where to change the code for a mock client. The mock client uses Goldfish and a finality gadget that is not Casper FFG. All line numbers come from commit 4a9884d6d5.

00 Summary

Gossipsub and fork choice connect in three ways. The three ways are different from each other.

  • A block goes into fork choice from the gossip goroutine. The state transition runs on this path. One write lock holds for the full operation.
  • An attestation does not go into fork choice from gossip. The handler writes the attestation to a pool. Two timers move the attestation into fork choice about one slot later. blockchain.AttestationReceiver has no insert method.
  • The gossip validator reads fork choice many times. It writes fork choice one time. The reads are InForkchoice, FinalizedCheckpt, ShouldIgnoreData, VerifyLmdFfgConsistency and AttestationTargetState. The write is RecordBlockForEquivocation. A feature flag controls the write.
Primary fact

Prysm has no filter_block_tree function. Casper FFG limits LMD-GHOST at four locations. The first location is one boolean expression at forkchoice/doubly-linked-tree/node.go:25. The second location is the start point of the tree search at store.go:32. The rest of the package is weight arithmetic. Weight arithmetic does not know which finality gadget made the numbers.

03 Timing

There is no central scheduler. Each slot action has its own goroutine and its own timer. All timers use one genesis time. A deadline is a fraction of the slot in basis points. On a 12 s slot, 3333 BP is 4 s.

04 Where Casper FFG limits LMD-GHOST

There are four locations. The ochre items go away with a new finality gadget. The teal items are weight arithmetic and do not change.

Read these 20 files in this order. Each file is easier to understand after the file before it.

Warning — a new topic needs five changes

Change these five files, or the topic does not work. One: p2p/topics.go — the format constant and an entry in allTopics. Two: p2p/gossip_topic_mappings.go — subscribe panics if the map entry is nil. Three: p2p/gossip_scoring_params.go. Four: sync/decode_pubsub.go, if the topic has subnets. Five: p2p/subnets.go. The third file is the dangerous one. Its default branch gives an error, SubscribeToTopic then fails, and subscribeWithBase writes a log line and returns nil. The result is a topic that is registered but never subscribed, with no clear failure.

Three items that need no change

chain.HasBlock (receive_block.go:458) reads the database and the initial sync cache. It does not read fork choice, so the pending queue continues to work. The data availability wait (receive_block.go:115) runs before the lock and before InsertNode. Availability is thus already a barrier before the insert. The initial sync path (process_block.go:185) never calls Head(). Your Goldfish code must be correct only on the live gossip path.

09 Warnings

These items cause faults that are difficult to find.

Feature flags change the validation path

The attestation seen-cache and the bad-block check at validate_beacon_attestation.go:105–118 are inside an if !s.slasherEnabled block. With the --slasher flag, neither check runs. The one gossip write to fork choice needs features.TrackEquivocations. The attestation pool has two different implementations. EnableExperimentalAttestationPool selects one.

A new topic can fail with no clear message

If you do not add the case to p2p/gossip_scoring_params.go, the default branch gives an error. SubscribeToTopic then fails. subscribeWithBase writes a log line and returns nil. The topic is registered but never subscribed. There is no clear failure. If you forget the gossip_topic_mappings.go entry, subscribe panics, which is easier to find.

Some code looks live but is dead

Service.CanSubscribe, checkSubscribable and FilterIncomingSubscriptions in p2p/pubsub_filter.go are not connected to the router. pubsubOptions uses the library filter instead. On the Gloas path, no code satisfies RequireMessageNotSeen. Therefore PayloadAttMsgVerifier.VerifiedPayloadAttestation() can never return a value on the gossip path. The real check is inline.

The lock rules are not the same everywhere

ReceiveBlock holds the write lock from :124 to the return. But validateExecutionOnBlock takes the same lock from inside an errgroup goroutine (:669–676). At that point ReceiveBlock does not hold the lock. If you take the lock earlier, the node deadlocks. Also, sendFCU releases the lock and takes it again. It then starts a goroutine that takes the lock a third time. The engine call therefore occurs after ReceiveBlock returns.

Two validators use two different orders

validate_beacon_attestation.go does InForkchoice, then VerifyLmdFfgConsistency, then AttestationTargetState. validate_aggregate_proof.go does VerifyLmdFfgConsistency, then InForkchoice, then AttestationTargetState. If you change one call, check both orders.

Pool 2 has no expiry

DeleteForkchoiceAttestation has two callers. Both are in the read loop. pruneExpiredAtts does not touch pool 2. An attestation that fails the “block and state present” test stays in the pool with no limit. With slot-scoped Goldfish votes, this becomes a memory fault and a correctness fault.

10 The two layers

The system has two layers. Each layer has its own protocol. One function connects them.

  • The available chain (AC) is Goldfish. It makes one block for each slot. It gives fast confirmation. The finality gadget treats it as a black box. The specification says so at :1225: “We treat the AC's internal structure as a black box; see, e.g., the Goldfish protocol for a concrete instantiation.” height_filter_healing.tex:75, :97, :250 builds on Goldfish directly, including Goldfish committees and Goldfish view-merge.
  • The finality gadget (FG) is Fresh Simplex with Height Filter and Timeouts. It counts heights, not slots. It makes blocks irreversible.
  • The connection is one function: getConfirmed(store, Ω) at :559. The gadget supplies the walk-from block and the set of allowed blocks. Goldfish supplies Ω, which selects one block from that set.
This is the decoupling

The specification says at :512: “Ω represents the state of the available chain — whatever extra information the validator uses to disambiguate among viable descendants of the walk-from block.” And at :517–518: “The choice among admissible descendants is left to Ω. Different validators may pass different Ω.” In Prysm terms: getConfirmed is store.head (store.go:22). The walk-from block is the anchor at store.go:32. Ω is what bestDescendant does today.

11 The gadget: state and messages

The model is n validators, of which at most f are adversarial, with n ≥ 3f + 1. A quorum is ≥ 2n/3 validators. Two quorums share more than f validators, so they share at least one honest validator. :155–157

Warning — the quorum counts validators, not stake

Every threshold in the specification counts validators: |{i : targets[i] = T}| ≥ 2n/3. Prysm counts effective balance everywhere. A mock must choose one. If you keep balances, you must restate all the safety arguments in balance terms. If you count validators, the mock is not comparable to mainnet numbers.

12 The algorithm

The rules in order. The branch order is normative. :246–247, :275

Height advances by exactly 1, in two ways

A height is not a slot. A height covers as many slots as it needs. Only two things advance it: a justification quorum, or a timeout quorum. :159–162

The state machine

stateTransition(st, B):                          // per-block entry point, :289
    while st.s < B.slot: st = processSlot(st)      // advance through empty slots
    st = processBlock(st, B)
    st = processHeight(st)                          // close events that B's own votes enabled
    return st                                       // now st.s = B.slot and st.L = B

processSlot(st):                                    // the ONLY place s increments, :299
    if st.L.slot < st.s: st = processHeight(st)     // this slot is empty on this chain
    st.s = st.s + 1
    return st

processBlock(st, B):                                // :308
    assert st.s == B.slot
    st.L = B
    for v in B.votes: st = processVote(st, v)
    return st

processVote(st, v):                                 // :316
    i = v.validator
    if v.target == nil:                             // timeout vote
        if v.height == st.h: st.timeouts[i] = true
    else:                                           // justification vote
        fresh = v.height == st.h
            && isStrictAncestor(v.target, st.L)    // STRICT. not "or equal".
            && v.target.slot >= st.sH              // target is inside the current height
        if fresh:
            st.targets[i]  = v.target
            st.timeouts[i] = true                   // a justification also sets the timeout marker
    // the P gate runs for EVERY vote, timeout votes included, and ignores freshness
    if v.finalizeHeight == st.hJ && v.finalizeTarget == st.J:
        st.P = st.P + {i}
    return st

processHeightEvents(st):                            // branch order is normative, :343
    // (i) FINALITY -- falls through, does not return
    if |st.P| >= 2n/3: st.F = st.J

    // (ii) JUSTIFICATION -- returns
    T = the target with the most entries in st.targets   // nil if targets is empty
    if T != nil && |{i : st.targets[i] == T}| >= 2n/3:
        st.J = T;  st.hJ = st.h;  st.P = {}          // hJ takes the PRE-increment h
        st.h = st.h + 1;  st.sH = st.s
        reset st.targets, st.timeouts
        return st

    // (iii) TIMEOUT CERT
    if |{i : st.timeouts[i]}| >= 2n/3:
        st.h = st.h + 1;  st.sH = st.s
        reset st.targets, st.timeouts
        // J, hJ, P and F are NOT touched
    return st
Warning — three details that are easy to get wrong

The freshness test uses a strict ancestor test. A vote for the head block itself does not count. :323
The finality branch falls through. It does not return. A single call can finalize and then advance the height. :343–345
P is cleared only in the justification branch. A timeout does not clear it. :346–356

The store

onBlock(store, B):                                  // :530 -- this is Prysm's InsertNode
    assert B.parent in store.tree
    assert isAncestorOrSelf(store.F, B)             // nothing below the finalized block is accepted
    store.tree = store.tree + {B}
    st = stateTransition(store.state[B.parent], B)
    store.state[B] = st
    store.hMax = max(store.hMax, st.h)              // BEFORE the two guards below
    store = updateJustified(store, st.J, st.hJ)
    store = updateFinalized(store, st.F)
    return store

updateJustified(store, J2, h2):                     // :543 -- F filter, then lex running max
    if isAncestorOrSelf(store.F, J2)
       && (h2, hash(J2)) > (store.hJ, hash(store.J)):    // lexicographic
        store.J = J2;  store.hJ = h2
    return store

updateFinalized(store, F2):                         // :551 -- THREE guards
    if isStrictDescendant(F2, store.F)
       && isAncestorOrSelf(F2, store.J)
       && isViable(store, F2):                     // the viability guard
        store.F = F2
    return store

isViable(store, B):                                 // :487 -- the height filter
    // a leaf is viable if its state height is at most one behind the frontier
    // an internal block is viable if any descendant of it is viable
    return exists leaf L >= B with store.state[L].h >= store.hMax - 1

getConfirmed(store, omega):                         // :559 -- Prysm's store.head
    R = store.J if store.hMax == store.hJ + 1 else store.F   // the two-way cascade
    return a block B in viable(store) with
        isAncestorOrSelf(R, B) and store.state[B].h >= store.hMax - 1,
        selected by omega                          // <-- Goldfish decides here
Why the cascade has two branches

A justification at height h forces that chain to height h + 1. So hMax ≥ hJ + 1 always holds. The gate hMax == hJ + 1 therefore holds exactly when no timeout has pushed any chain past the justified block's height. When the gate fails, store.J is stale, and the walk starts from store.F instead. :511–518. This one line is the whole difference from Prysm, which always walks from the justified root.

How a validator builds its vote

The validator keeps a third state, called Δ in the specification. It holds only the validator's own past votes. The specification is explicit that this belongs on the validator client, and that the store belongs on the beacon client. :878

getBaseVote(store, omega):                          // :892
    T  = getConfirmed(store, omega)                 // the target IS the confirmed block
    return (me, store.state[T].h, T, store.state[T].hJ, store.state[T].J)
    // only the last three fields are read off the target's post-state

getFinalVote(delta, v):                             // :899 -- runs on the VALIDATOR client
    (i, hc, T, hf, Tf) = v
    assert hc > hf
    if delta.locked[hc]:      T = delta.target[hc]  // locked: re-send the lock target
    elif delta.target[hc] != nil: T = nil           // voted here before, not locked: time out
    // the finalize gate -- identical in all three branches
    if delta.target[hf] != Tf or delta.timedOut[hf]:
        (hf, Tf) = (nil, nil)                       // cannot commit safely, so do not commit
    v2 = (i, hc, T, hf, Tf)
    recordVote(delta, v2)
    return v2

slashing, rule E1:                                 // :254 -- ONE rule, that is all
    a validator is slashable if it signed a and b with
        b.finalizeTarget != nil
        and a.height == b.finalizeHeight
        and a.target != b.finalizeTarget
    // note: a timeout vote (target = nil) conflicts with any finalize commitment
    // note: two justification votes at one height are NOT slashable by themselves

17 Not settled — stub these

The specifications mark these parts as incomplete. Do not implement them from the text. Stub them and record the choice you made.

  • Seven store properties have no proof. The property environments at :1817–1860 state compatibility, monotonicity, target dominance and visibility of getConfirmed. No proof attaches to any of them anywhere in the document. The liveness argument depends on them.
  • The liveness argument is marked WIP in the overview (main.tex:37).
  • Rprime has no initial value. The healing modification adds the field and only onVotingTime ever writes it. The modified getConfirmed reads it without a guard. The genesis store at :526–527 does not set it. getConfirmed is therefore undefined before the first voting time. Set it to genesis.
  • The stability criterion is abstract. :1043–1044 says “The selection criterion — e.g. depth past a state-height advance, observed-stability duration, or another application-defined predicate — is left abstract here.” Pick the simplest one for a mock: the finality-vote target.

Warning — two clocks and one lock
