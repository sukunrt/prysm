The decimal differences from older tables come from consistently distinguishing outer log timestamps from the BN's `sinceSlotStartTime` field. Neither is a packet-arrival timestamp or a historical runtime profile. The table locates recorded events; it does not equate every interval between events with active CPU time inside one function.

**Why the preflight failures prevent proposals.** The exact source gives each slot an absolute deadline of `genesis + (slot+1)*12s`. `runner.go` calls `RolesAt` synchronously and dispatches proposer work only afterward. `RolesAt` includes sync-committee selection. The fresh context created after role discovery uses the same absolute deadline; it does not renew the budget. Thus slots 2, 3, 4, 7, 11, and 12 have a source-backed dependency chain: synchronous preflight has not returned by the deadline → proposer starts with an expired deadline → RANDAO prerequisite fails → block RPC is not issued. The paired errors are not two independent failures.

The preflight start is absent from the historical logs. Proposer settings, attester aggregator selection, and other work precede the logged failing call. It is therefore incorrect to say that each individual sync RPC demonstrably occupied all twelve seconds. For the five sync-index cases, the server path includes a per-slot async lock and, on a cache miss, head-state access and slot processing. Slot 4 instead reaches the signing-domain path. The logs do not time these internal operations.

Slot 1 has a separate limit. A different role's output proves role dispatch by `+9.915` (`validator.log:686`), but no markers record proposer-goroutine start, acquisition of the proposer-role lock, domain-cache lock acquisition, or DomainData handler admission. Source shows the RANDAO DomainData handler computes from configuration and the genesis validators root; it does not scan the registry, obtain parent state, or call the EL. That rules out expensive RANDAO handler state processing as the explanation. It does not identify where the proposal lost its budget before DomainData returned.

**Why the payload failures are not slow EL construction.** Slots 5, 6, 8, and 9 have matched payload IDs and snooper request/response records. The proxy logs prompt successful responses, while the BN caller subsequently returns a timeout. Exact source wraps the Gloas `getPayload` call in a 300 ms context. After local retrieval fails, the builder tries a P2P bid; the logs explicitly record that none is available, and source immediately returns an error. These records establish the missing required input and the reason the build cannot continue.

They do not establish when the response body reached the BN kernel, when its reader ran, or when decoding completed. The previous packet/runtime experiment resolves those distinctions for its own three-node run; the historical snooper does not. Likewise, late first build logs in slots 5 and 8 establish a small remaining budget, but do not identify the upstream dispatch delay or prove that the remaining 1.88/0.81 seconds was intrinsically insufficient.

**Why packing errors have different meanings.** `buildBlockGloas` starts a consensus-field goroutine, obtains/selects a payload on the caller, then waits for the consensus goroutine before computing the block state root. If local payload and fallback both fail, it returns before the wait. This makes the late packing cancellations in slots 5, 6, 8, and 9 consequences of abandoned work, rather than the event that ended the request.

Slots 10 and 14 reach the wait because payload selection succeeds. Their late packing-error logs show that the required branch had not finished on time. The packing error itself is handled by putting empty deposits/attestations in the candidate; it is not directly propagated as the final build error. Once the branch finally returns, state-root processing sees cancellation and fails. The precise chain is unfinished consensus work → deadline expires while the result is required → late branch return → state-root cancellation/build failure. The logs do not expose candidate counts, pool-lock owners, or the branch's CPU/runtime history. Calling this proven quadratic packing or a measured 29/41 seconds of packing CPU exceeds the evidence.

Slot 13 stops earlier. The wrapper places cancellation observation inside the slot-processing path called during parent-state preparation. It does not prove that the entire 10.721-second handler-log-to-error interval was spent executing slot transitions. That interval also includes earlier handler checks and parent/head access. The cache may observe an already canceled context at its first check. The separate FCU response cannot be inserted into this handler's critical path merely because it occurs between the handler's two logs.

The vote records are validation-accepted records, emitted before subscriber insertion into fork choice. They establish the signed root split, not the exact store snapshot at the deciding instruction. The preceding calculation is consequently a source-backed explanation using the observed cohort, not a recovered per-node dump of the historical decision. The archives also do not divide node 69/node 93's late local imports into wire-delivery delay versus local validation/import scheduling. Those finer attributions remain unrecorded.

**What survives scrutiny from the previous explanations.** The genesis-count defect is real: the genesis-root target-round-0 checkpoint uses a slot-0 state, and `ActiveValidatorCount` refuses its cached-count return at slot 0. Historical accepted FFG messages prove that the affected validation path ran. The earlier local ablations demonstrate that removing repeated scans can remove scan-dominated CPU, lock queues, HTTP-reader starvation, and proposal failures under that experiment's load. That is stronger than an untested hypothesis, but it is not a historical profile of nodes 169, 35, 85, or the other owners.

The remaining Xatu logs do not close the RPC gap. Neither the number of archived nodes nor a successful separate reproduction restores timestamps, pool contents, lock ownership, packet delivery, or scheduler events that the original run did not record.
