# Spec-test survey, 2026-08-21

A read-only sweep of every consensus spec-test vector suite in the tree, taken on
change `vopzvxty` (empty, on `wuvqqozt` "blockchain: the genesis parent reveals no
execution requests"). Nothing was fixed, skipped or edited; this note is the only
change.

**Headline: 8 spectest targets, 4 fail. 496 vector cases fail out of 11,544 runnable
pyspec vectors (4.3%). 486 of those 496 are one deliberate deviation — the FFG target
shift. 10 are unexplained and are listed first.**

The goldfish head walk, the available-attestation store, the round structure and the
Heze state shape are all dormant under both spec presets: `HezeForkEpoch` is
`FarFutureEpoch` in `config/params/mainnet_config.go:38` and
`config/params/minimal_config.go:115`, and every goldfish entry point is behind
`goldfishActiveAt` (`beacon-chain/forkchoice/doubly-linked-tree/goldfish.go:204`).
So none of them can explain a spec-test failure, and none of the failures below is
attributed to them. `SLOTS_PER_ROUND` equals `SLOTS_PER_EPOCH` in both presets
(mainnet 32, minimal 8), so the round-based committee math in
`beacon-chain/core/helpers/beacon_committee.go` is numerically identical to stock.

**Observed shape.** In eight of the ten the returned head root is the *anchor* root.
Verified by hand for `mainnet/gloas/get_head/split_tie_breaker_no_attestations`: the
vector's anchor root is `0xe2ad2b8d…8375c4`
(`tests/mainnet/gloas/fork_choice/get_head/pyspec_tests/genesis/steps.yaml`), the
expected head after importing the slot-1 block is `0x76bf14e7…fcd9e5`, and Prysm
returned `0xe2ad2b8d…8375c4` — it never left genesis. The same `got` root appears in
`discard_equivocations_on_attester_slashing` and
`proposer_boost_root_same_slot_untimely_block` in the same preset.

**What separates these from the Gloas fork-choice vectors that pass.** The passing
head vectors (`genesis`, `chain_no_attestations`, `get_head_empty_payload_tiebreak`,
`get_head_full_payload_tiebreak`, `shorter_chain_but_heavier_weight`, `basic`,
`proposer_boost`, `proposer_boost_is_first_block`,
`get_parent_payload_status__genesis_empty_block_hash`) all import each block during
its own slot, so the block takes proposer boost. Every failing case imports a block
that gets no boost — either the tick is already past the block's slot
(`split_tie_breaker` ticks to 24 then imports slot-1 blocks; `discard_equivocations`
ticks to 72 then imports slot-3 and slot-4 blocks) or the block is untimely within
its slot (`proposer_boost_root_same_slot_untimely_block`, tick 51). Proposer boost is
*not* disabled here — the fork's gate on it is
`beacon-chain/forkchoice/doubly-linked-tree/proposer_boost.go:19`
(`!s.goldfishActive() && s.shouldApplyProposerBoost()`), and `goldfishActive()` is
false under both presets — so a zero-weight child of the anchor is simply not being
picked up by the Gloas payload-node best-descendant walk.

**Classification: UNKNOWN, leaning "real bug".** Two candidate causes, neither
confirmable without a build at an older revision:

1. `beacon-chain/forkchoice/doubly-linked-tree/store.go:174-186` (change
   `mlouxtor`, `c3a83dd4`, "forkchoice: genesis's payload is the execution genesis
   block, not the zero hash") now creates a **full** payload node for a Gloas genesis
   block. The spec vectors assert genesis's head payload status is `0` (EMPTY). A
   slot-1 block whose bid names the execution genesis hash therefore hangs off
   genesis's *full* node (`gloas.go:66-70`, `resolveParentPayloadStatus`), while
   `choosePayloadContent` (`gloas.go:319-345`) may resolve genesis to the empty node,
   whose child list is then empty.
2. A pre-existing gap in `updateBestDescendantPayloadNode` /
   `leadsToViableHead` for zero-weight children in the ePBS two-node tree, inherited
   from the upstream Gloas work and unrelated to this fork.

**To settle it:** build `//testing/spectest/mainnet/gloas:go_default_test` at change
`zolrlsqn` (the change immediately before the four genesis commits `mlouxtor`,
`lklwxtxk`, `kyvzlwlr`, `wuvqqozt`) and run
`--test_filter='TestMainnet_Gloas_Forkchoice/(split_tie_breaker_no_attestations|discard_equivocations_on_attester_slashing)'`.
If they failed there too, cause 2; if they passed, cause 1 and the genesis-full-node
change needs a fork-choice-side companion.

## Classification

### Group A — FFG target shift. 486 of 496 cases. EXPECTED-DEVIATION.

**Mechanism.** `beacon-chain/core/helpers/block.go:100-109` replaces the spec's
`get_block_root(state, epoch)` with `FFGTargetRoot`, which returns the block root at
`compute_start_slot_at_epoch(epoch) - 1` instead of `compute_start_slot_at_epoch(epoch)`
(epoch 0 clamps to slot 0). Change `kztuytom` / `075dd50084a9`, "forkchoice, state:
shift the FFG target to the slot before the epoch". **It is unconditional — no version
gate, no feature flag, no fork epoch** — because the forkchoice side
(`beacon-chain/forkchoice/doubly-linked-tree/store.go:135-148`, which sets `n.target`
to the deepest ancestor in an earlier epoch) has to agree with it or
`VerifyLmdFfgConsistency` rejects every vote.

Four call sites carry it into the pure state transition:

- `beacon-chain/core/altair/attestation.go:365` — `MatchingStatus`, i.e.
  `is_matching_target`, so participation flags differ for any attestation whose target
  root falls on a slot where the two rules disagree.
- `beacon-chain/core/epoch/precompute/attestation.go:121` — the phase0
  `PendingAttestation` target match.
- `beacon-chain/core/epoch/precompute/justification_finalization.go:164` and `:172` —
  the current- and previous-epoch justified roots written by
  `weighJustificationAndFinalization`.

**Sub-groups and their failure signature:**

| sub-group | cases | signature |
|---|---|---|
| `epoch_processing/justification_and_finalization` | 96 | post-state diff at `helpers.go:64/66/67` |
| `fork_choice` + `sync` (block import) | 194 | `builder.go:121` "could not validate state root" |
| `transition/core` | 82 | `transition.go:99-116` "could not validate state root" |
| `finality/finality` | 70 | `finality.go:65-75` "could not validate state root" |
| `random/random` | 26 | post-state diff / state-root mismatch |
| `sanity/blocks` (minimal only) | 10 | state-root mismatch |
| phase0 `finality` | 8 | `runner.go:70` "could not validate state root" |

**Sample verification, one per sub-group family:**

- `minimal/gloas/epoch_processing/justification_and_finalization/123_ok_support`: the
  post-state diff is exactly `current_justified_checkpoint.root`, expected
  `0xaaaa…aaaa`, got `0x0000…0000` — no attestation matched the target, so nothing
  justified. That is `FFGTargetRoot` naming `block_roots[start-1]` while the vector
  built its attestations against `block_roots[start]`.
- `mainnet/phase0/epoch_processing/justification_and_finalization/*`: same group,
  reached through `precompute/attestation.go:121` instead, reported as
  `helpers.go:64: Post state does not match expected`.
- `mainnet/phase0/finality/finality_rule_1`: `runner.go:70 … could not validate state
  root, wanted 0xa771…c2f4, received 0x62cf…fbb9` — the justification difference
  changes the state root at the epoch boundary.
- `minimal/deneb/fork_choice/justification_update_beginning_of_epoch` and 25 siblings:
  `builder.go:121 … could not validate state root, wanted 0x9872…4bec, received
  0x3ccb…aa41`. The identical wanted/received pair recurs across many minimal
  fork-choice vectors because they share the same first divergent block.
- `mainnet/altair/fork_choice/basic_is_parent_root` is the *only* mainnet non-Gloas
  fork-choice failure per fork: mainnet's 32-slot epochs mean most fork-choice vectors
  never cross an epoch boundary, so only that one reaches the shifted rule. Minimal's
  8-slot epochs make 26-27 per fork cross it. That asymmetry is itself evidence the
  cause is epoch-boundary FFG behaviour and nothing else.

**Why this is expected and not actionable:** the shift is the point of the decoupled
design — a validator casting its finality vote at the start of an epoch's first slot
has not seen that slot's block yet, so the target names a block that already exists.
The upstream vectors assert the unshifted rule. There is no way to satisfy both.

### Group B — Gloas head selection. 10 cases. See "UNEXPECTED" above.

### Not implicated by any failure

- **Available attestations** (`proto/prysm/v1alpha1/heze.proto`,
  `beacon-chain/forkchoice/doubly-linked-tree/goldfish.go:174`
  `InsertAvailableAttestation`): dormant, gated on `HezeForkEpoch`. The gossip topic is
  not even registered under either spec preset.
- **Goldfish gate / stop-retreat / round proposal**
  (`goldfish.go:325`, `:340`, `:438`, `:463`, `:490`): head selection still goes through
  `bestDescendant`, because `store.go:30-34` only diverts to `goldfishHead()` when
  `goldfishActive()`.
- **SLOTS_PER_ROUND / Round** (`config/params/config.go:73`,
  `consensus-types/primitives/round.go`): both presets set
  `SlotsPerRound == SlotsPerEpoch`, so `beacon-chain/core/helpers/beacon_committee.go`
  and `beacon-chain/core/gloas/pending_payment.go:86` compute stock values.
- **Heze state / fork** (`proto/prysm/v1alpha1/heze.proto:64`): there are no Heze spec
  vectors run — `tests/*/heze/` exists on disk but no Prysm suite reads it, and the
  fork here reuses the name for a genesis-only consensus fork rather than upstream's
  FOCIL fork.
- **Genesis edge cases** other than the full-node question in Group B:
  `beacon-chain/blockchain/gloas.go:137` (genesis parent reveals no execution
  requests), `beacon-chain/blockchain/process_block.go:1218` and
  `beacon-chain/rpc/prysm/v1alpha1/validator/proposer_execution_payload.go:366` (empty
  parent builds on `latest_block_hash`), and
  `beacon-chain/forkchoice/doubly-linked-tree/forkchoice.go:575` (`CommonAncestor`
  compares consensus nodes) sit on paths the spec runners do not exercise.
  `get_parent_payload_status__genesis_empty_block_hash` passes.

## Addendum (same day): the 10 UNEXPECTED cases attributed

Re-ran all Gloas forkchoice vectors with `mlouxtor` (genesis full-payload node) reverted: the
same head-selection cases still fail. The failures are the pre-existing gap in the ePBS
best-descendant walk, not the slot-1 genesis fix. They exercise stock Gloas LMD head selection
(proposer-boost edge cases), which the Heze/goldfish runs do not drive; every live run selects
correct heads. Classification: pre-existing stock-Gloas conformance gap, dormant for this fork.
