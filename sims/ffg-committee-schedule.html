Staggered FFG committees

Implementation plan

Today, with committees per slot = S as in the recorded runs, each subnet has one FFG committee per slot. All members of that committee send their vote at the same time, so the subnet gets a burst of single votes. This change puts X committees on each subnet in each slot and sends them one after the other. Each committee has its own aggregators. The last committee's aggregate publishes at the existing aggregate due.

Scope. In scope: one flag, the committee count, the send and aggregate times in the validator client, and forwarding the flag in the Shadow harness. Out of scope: new deadlines or late-vote checks in the pool, RPC, gossip or P2P code; new message formats or topics; changes to aggregator selection; changes to blocks, payloads, blobs, PTC, Goldfish votes or other traffic; new validation checks or limits; new metrics or logs; unrelated refactors. X <= 1 keeps current behavior.

Flag

--ffg-committees-per-subnet-per-slot=X

The beacon node, the validator client and the Shadow harness accept the flag. The default is 1. The value is an unsigned integer; 0 and 1 both mean disabled. The beacon nodes and validator clients of one simulation must use the same value. The harness forwards one value to all of them.

Committees

Let S = ATTESTATION_SUBNET_COUNT. When X >= 2, the committees-per-slot count is X * S. The existing clamp to MAX_COMMITTEES_PER_SLOT stays, so use X * S <= 64 (committee_bits is a Bitvector[64]). The existing shuffle and committee construction use this count. Do not build the old committees and then split them.

The existing subnet mapping gives subnet = c % S for committee index c, because the count is a multiple of S. The position of the committee on its subnet is i = floor(c / S). Example: with S = 2 and X = 3, subnet 0 has committees 0, 2, 4 and subnet 1 has committees 1, 3, 5. Each validator still votes once per round. Validators move into more, smaller committees.

Schedule

Let D be the existing aggregate due in milliseconds from slot start: AGGREGATE_DUE_BPS_GLOAS from the Gloas fork, AGGREGATE_DUE_BPS before it. The committees share the time before D equally:

B[i] = floor(i * D / X), for i = 0 .. X

position i sends at:          slot_start + B[i] + jitter
position i aggregates at:     slot_start + B[i + 1]
last aggregate (i = X - 1):   slot_start + B[X] = slot_start + D

All subnets use the same schedule. After D there are no scheduled single votes. That time is for aggregate propagation. Other traffic continues for the whole slot.

Rules when X >= 2

  1. Send. Wait until slot_start + B[i] plus the existing --decoupled-ffg-vote-jitter delay. Then run the existing attest path: get the attestation data, sign, publish once. Do not get the attestation data or sign before this time. The duty lookup that gives i can come first. A block arrival does not release the vote early. --decoupled-ffg-vote-spread and the wait for the attestation due or a block do not apply.
  2. Data. The existing per-slot attestation data cache in the validator client does not change. If the validator client already got data in this slot, a later position uses that data.
  3. Aggregate. Each committee uses the existing aggregator selection and target. Each selected aggregator waits until slot_start + B[i + 1], then gets its committee's aggregate from its beacon node, signs and publishes on the existing aggregate topic. The existing empty-pool, candidate-selection and duplicate-duty behavior stays. There are about X times more aggregates per slot.
  4. Late votes. No new rule. Gossip validation keeps its existing slot window. A vote that arrives after its aggregator got the aggregate still goes into the pool; it is not in that aggregate. The validator client does not skip a late send.
  5. Beacon node diagnostics. The FFG summary and vote seats tick at D, which is now the last aggregate trigger. They do not change.

Evaluate

Compare the baseline (X = 1) with X = 2, 3, 4. Use the same D in all arms, so the last aggregate publishes at the same time. Keep validators, round length, topology, bandwidth, latency, other traffic and seeds the same. In the baseline, set --target-committee-size so that committees per slot = S.

  • Peak single-vote messages and bytes per 100 ms per subnet.
  • Aggregate publish time and publish-to-receive latency (p50, p95, p99).
  • At slot end, distinct voters covered by the aggregates each node received. Count each signer once.
  • Latency of other traffic, to see contention move to the aggregate topic.

A larger X gives smaller bursts, but each committee has less time and there are more aggregates. Some analysis scripts assume one aggregate due (shadow/analysis/latency-report.sql uses 6000 ms). If a measurement is not available from existing output, report that. Changes to analysis tools are a separate task.
