What to change in Prysm to test the networking of decoupled consensus

Decoupled consensus adds one new gossip topic and raises the vote rate four times. This document lists the code you must change to put that on the wire. The consensus logic can be wrong. The network behaviour must be correct.

Must be real The network sees it. Get it right. Safe to stub The network does not see it. Any value is acceptable.
How to read this

00 The goal

You want to measure the network cost of decoupled consensus. You do not want to implement it.

Decoupled consensus has two parts. Goldfish is the available chain. It selects the head. A finality gadget confirms blocks. The finality gadget is not Casper FFG.

Today one attestation carries three things at once: the head vote, the source checkpoint, and the target checkpoint. Decoupled consensus splits that. The head vote goes to Goldfish. The finality vote goes to the finality gadget. They become two separate messages with two separate schedules.

The rate changes as well. A validator attests once per epoch, which is 32 slots. A validator casts one finality vote per voting round. A voting round has m sub-rounds, and one sub-round is one available-chain slot. With m = 8, a validator votes once per 8 slots. That is 4 times the attestation rate.

The question to answer

The finality vote replaces today's attestation, on the same subnets, at 4 times the rate. The Goldfish head vote is the added stream. Can the network carry both? At which validator count does it fail? These are networking questions. You can answer them with wrong consensus values.

So the plan is: build the real message path, and stub everything behind it. A validator signs a vote with correct field sizes and incorrect field contents. It sends the vote at the correct time on the correct topic. The receiver checks the signature, puts the vote in a map, and does nothing more. The network cannot tell the difference.

★ The plan — clone the attestation path

The finality gadget vote has the same network shape as an Ethereum attestation. Do not build a new path. Copy the one that exists. Sections 05 to 07 give the file-level steps that this plan uses.

The whole design difference is one number

A voting round of m = 8 sub-rounds means a validator votes once per 8 slots. Today a validator attests once per 32 slots. That is 4 times the rate. Every other property of the message path is the same.

Option A — change the period. No new code.

Set SlotsPerEpoch = 8. Each validator then attests once per 8 slots. The per-slot message count becomes n/8 instead of n/32. That is the 4× target, on the real path, with real subnets, real aggregation, real block inclusion, and real fork choice.

Do this first

Option A gives you a real 4× measurement in one afternoon. If the mesh carries it, you know the answer before you write any new code. If it does not, you know that too, and Option B cannot make it better.

Note the limit: Option A covers only the finality stream. It does not model the Goldfish vote. The available_attestation topic adds 512 messages per slot on top, at any validator count. Option B and the ★★ section add that stream.

Option B — clone the attestation topics. Recommended.

Keep the chain on its normal epoch. Add one new message type that copies the attestation path exactly, with an assignment period of 8 slots.

Be clear about one simplification. In the target protocol, the finality attestation replaces today's attestation — the old message does not survive. In the Option B mock, today's attestations keep running, because they keep the chain finalising and healthy. The mock therefore carries one extra stream at n/32, which overcounts traffic by a small, known amount. Subtract it, or ignore it: at 4 times the rate, the new stream dominates.

Option B tests a timing that Option A cannot

The finality vote's fields freeze at the round start: "Its FG fields are selected once in the round's first slot" (validator.md:259). The vote does not depend on the current slot's block. So it can go out at the start of the slot. Today's attestations wait for one third of the slot, so they do not compete with the block. A slot-start vote shares the wire with block propagation. Option B has its own producer, so it can publish at slot start and measure that collision. Option A cannot: it reuses the attestation duty, which is fixed to the attestation deadline.

One caveat: the head field inside the vote "is read live when the assigned duty is emitted" (validator.md:71). A slot-start vote therefore names the previous head. The mock accepts this — the content can be wrong, the timing cannot.

★★ Available attestation — the one new topic

An executable specification exists. It is more exact than the papers, and it answers the topic question completely. Read it before you write code.

The load is constant

The Goldfish load is flat. AVAILABLE_COMMITTEE_SIZE is 512 at every validator count. The worst case on the new topic is 512 messages of 201 bytes per slot. That is 103 KB per node per slot before aggregation. That does not change if you go from 4 000 validators to 1 000 000. All the growth is in the finality attestation.

Warning — a global topic with 512 publishers per slot

Every node receives every available attestation, because the topic is global. At 512 publishers per slot that is about 43 messages per second, on top of the block topic and the aggregate topic. Prysm has no global topic with this publish rate today. Measure it on its own before you combine it with the finality load.

What the mock needs

  • One new global topic and its message type. Follow the 8 steps in section 05.
  • A committee selection function that returns 512 indices for a slot. Stub the shuffling; any deterministic choice works, because the network does not read it.
  • A producer that fires once per slot for the local validators in that committee.
  • A validator that decodes, checks the seen-cache, and returns ACCEPT. The specification's real validator is long; almost all of it is consensus checks you can drop.

01 The fidelity contract

Five properties make a network test valid. Keep these five correct. Change anything else.

Property 1 — byte count

Prysm marshals a message to SSZ and then compresses it with Snappy. See beacon-chain/p2p/encoder/ssz.go:37. Signatures and roots do not compress. So the wire size follows the SSZ size closely. Define the vote structures with the real field widths. Do not shorten a root to 8 bytes to save work.

Property 2 — message count

One vote per validator per round is the whole point of the test. Do not send one vote per node. A node runs many validators. Send one message for each validator that the node holds.

Property 3 — publish time

Gossipsub load is not flat. It arrives in bursts at the deadlines. If you publish at a different time, you measure a different network. Use the real deadline even if the vote content is random.

For this protocol, publish time is the defining change. The finality vote's fields freeze at the round start, so the vote goes out at the start of the slot. Today's attestations wait for one third of the slot, so they do not compete with the block. The slot-start vote does compete with the block. That collision is one of the main things to measure.

Property 4 — topic and mesh

A new topic makes a new mesh. Each mesh holds D = 8 peers by default. See beacon-chain/p2p/pubsub.go:23-36. Three new topics add three meshes to every node. That is more open streams and more heartbeat work. A global topic and a set of subnet topics behave very differently. Decide which one the specification means, then build that one.

Property 5 — gossip result

The topic validator returns ACCEPT, IGNORE, or REJECT. ACCEPT forwards the message. IGNORE does not forward it. REJECT does not forward it and lowers the peer score. See beacon-chain/sync/subscriber.go:514. A stub that returns IGNORE stops all propagation. The test then measures nothing. A stub that always returns ACCEPT removes the duplicate filter and measures too much traffic.

Warning

Property 5 is the easiest one to get wrong. A validator stub must still keep a seen-message cache and return IGNORE for a repeat. Prysm does this for attestations. Copy that pattern.

These sizes are design estimates

The specification defines a vote as a tuple, not as an SSZ container. The 184 and 144 byte figures come from adding the field widths that Prysm uses for the same kinds of field. For comparison, Prysm's PayloadAttestationMessage is exactly 146 bytes (proto/prysm/v1alpha1/gloas.ssz.go:1221) and SingleAttestation is exactly 240 bytes (proto/prysm/v1alpha1/electra.ssz.go:453). So the estimates sit in the normal range for this codebase.

Votes aggregate on chain, as attestations do today

Finality votes reach a block through BLS aggregation, exactly like attestations now. Votes that name the same height and the same target combine into one signature and one bit field. A block therefore carries a small number of aggregates, not one entry per validator.

Read the word "aggregate" in the specification text with care, because it has two senses. In the timing proofs it means "the proposer collects votes into a block". That is the inclusion step. The BLS combination is a different step. The specification does not describe it, because it is an engineering detail below the level of the proofs.

One thing changes: the period

A validator attests once per epoch, which is 32 slots. A validator casts one finality vote per voting round, which is m sub-rounds. One sub-round is one available-chain slot. With m = 8, the period is 8 slots instead of 32, so the vote rate is 4 times the attestation rate.

The quorum counts over the whole electorate, not over a committee. The specification keeps one target entry per validator: targets[1..n] (full/height_filter_and_timeouts.tex:199). The healing document says that finality counts use the electorate V and never committee units (height_filter_healing.tex:259). Goldfish committees apply to the available chain only.

This does not make each message larger

The quorum spans the electorate, but the votes do not all arrive together. The protocol divides the validator set across the m sub-rounds (full/height_filter_and_timeouts.tex:1157). Each slot then carries about n/8 votes, and each slot's aggregates cover about n/8 voters. This is the same shape as a per-slot committee today, but 4 times wider. Section 04 has the numbers.

Fold the stability vote into the finality vote

The specification pairs the two votes: "A validator that fails to cast its finality vote in voting round k also fails to cast a stability vote for round k; the two are emitted (or not) together" (full/height_filter_and_timeouts.tex:1161). They go out at the same instant, from the same validator, for the same round.

So send one message with both targets in it. This costs 32 more bytes and removes a whole topic, a whole validator, a whole handler, and a second set of subnets. The network sees the same message count at the same times.

One exception to check

Stability votes never go on chain. Finality votes do. If your mock includes votes in blocks, strip the stability field at inclusion time, or accept 32 extra bytes per voter in the block. At test scale, accept it.

Gossip aggregation — take the attestation design

The specification defines no aggregator role and no subnets. Ethereum does: individual attestations on 64 subnets, then chosen aggregators publish combined aggregates on one global topic. Because the vote shape matches an attestation exactly, take that design unchanged. See the ★ plan section.

Short answer

One thing is genuinely on top: the available_attestation topic, at 512 messages per slot, flat in validator count. The finality attestation is not extra traffic — it is today's attestation at 4 times the rate on the same topic. Nothing else adds a message.

One large item is out of scope

A round-start re-gossip duty would have made the round proposer replay a whole round of retained aggregate objects onto the existing topics. That would be by far the largest event in the design. It is out of scope, and it is expected to stay out. Section 11 records what it is and what to watch if it returns.

The finality attestation rate

The sub-round partition sets this. A sub-round is one slot, and only the validators assigned to that sub-round vote at it. So n/8 validators vote per slot, not n.

votes per slot   =  n / m          where m = 8 sub-rounds per voting round
today            =  n / 32         one attestation per validator per epoch
ratio            =  32 / 8  =  4

The formula ignores duplicate arrivals before the mesh settles, ignores control traffic, and assumes Snappy gives no gain on signature bytes. Use the table to choose a test size. Do not report it as a result.

04 The block growth effect

Finality votes go on chain as BLS aggregates. Blocks still get larger, but the cost is the bit field, not the signatures.

An aggregate holds one signature for many voters plus one bit per voter. Each voter therefore costs one bit on chain, whatever the aggregate grouping is. The block cost per slot is:

bit-field bytes per slot  =  (voters that slot) / 8

gadget, m = 8 sub-rounds   =  (n/8)  / 8  =  n / 64   bytes
today, 32-slot epoch       =  (n/32) / 8  =  n / 256  bytes
ratio                      =  4

plus 176 fixed bytes per aggregate (80 data + 96 signature)

Block growth is not a problem

Sub-round partition puts only n/8 voters in each slot. BLS aggregation puts each voter in one bit. The result is 4 times today's on-chain vote cost, and at one million validators that is about 12 KB more per block. The 10 MiB cap (config/params/mainnet_config.go:364) is far away. Do not spend effort here.

Two smaller costs go with it. Each aggregate adds 176 fixed bytes, so many small aggregates cost more than few large ones. The stability target is the second cost. If you keep it inside the vote and do not strip it at inclusion time, each voter adds 32 bytes to the block.

Where to look instead

The gossip load in section 03 is the real constraint, not block size. Measure that first. Return to block size only if you run above 100 000 validators.

Two behaviours of the publish path to know about

  • Publish blocks until a peer exists. PublishToTopic loops with a 100 ms sleep until the topic has at least one peer (beacon-chain/p2p/pubsub.go:93-104). At node start this delays the first votes. Discard the first epoch of measurements.

Safe to stub — signing

BLS signing costs about 1 ms per signature. At 512 validators on one node that is 512 ms per round, which distorts publish timing. Two options: sign once at start and reuse the same 96 bytes in every vote, or use a fixed 96-byte constant. Both keep the wire size exact. The second also removes signature verification cost on the receiver. Choose based on whether you want to measure verification load.

08 Change list D — the head rule is Goldfish

Decoupled consensus replaces both halves of Prysm's fork choice. Goldfish is the head rule, in place of LMD-GHOST. The finality gadget confirms blocks, in place of Casper FFG. Neither of the old rules survives.

What Goldfish is, in one paragraph

Goldfish (GHOST-Eph) picks the head from votes, like LMD-GHOST, with one change that matters for everything else: the votes are ephemeral. Only the current slot's votes count. A vote does not carry forward. LMD-GHOST does the opposite — it keeps each validator's latest message and reuses it every slot until the validator votes again.

Goldfish votes are the available attestations

The ★★ section already describes the message. AvailableAttestation carries beacon_block_root, which is the Goldfish head vote, from a 512-member committee, once per slot, on one global topic. That is the whole Goldfish input.

So Goldfish is not extra work on top of the plan. It is what the new topic is for. If the handler for that topic writes to a map that nothing reads, you have built the message but not the protocol.

Ephemerality is visible on the wire

This part reaches the network. The specification's gossip validator drops each message that is not for the current slot:

# consensus-specs/.../simplex/p2p-interface.md — validate_available_attestation_gossip
if data.slot != get_current_slot(store):
    raise GossipIgnore("available attestation is not for the current slot")

Compare Prysm today. An attestation is valid for gossip across a much wider window, and the seen-cache spans slots. A Goldfish vote is valid for exactly one slot. Three consequences:

  • The seen-cache for this topic is one slot deep. It is cheap, and it must be pruned every slot.
  • A late vote is not merely useless, it is dropped. So delivery latency turns directly into lost votes. That is a networking result you can measure.
  • There is no pending queue worth having for this topic. A vote whose block has not arrived is dead by the next slot.
Warning — this is the measurement Goldfish makes interesting

Under LMD-GHOST a slow vote still counts later. Under Goldfish it does not count at all. So the fraction of available attestations that miss their slot is the health of the available chain. Record it at every validator count and every latency setting.

10 Fidelity traps

These changes look like harmless stubs. Each one silently changes the network.

T1

One node, many validators, one message. The easiest mistake. A test network of 8 nodes with 512 validators must send 512 messages per round, not 8. Check the message counter before you trust any result.

T2

All nodes publish at the same instant. Real validators have clock skew and different processing delays. A test where every node publishes at exactly the same microsecond creates a burst that the real network would not see. Add a small random spread, or accept that you measure a worst case and say so.

T3

Snappy compresses fake data. If every vote carries the same constant root, Snappy compresses it far better than a real root. Fill root fields with random bytes. Signature fields too.

11 The syncer — out of scope

The syncer adds no gossip traffic in the version you are building. The re-gossip duty is removed for now, and it is expected to stay removed. Do not build it. This section records what it was, so you recognise it if it returns.

Status

Removed Build nothing for the syncer. If a later revision of the specification brings back a view-merge relay, come back to this section and to the traffic arithmetic in section 03.

What a syncer is

Honest validators do not always hold the same view. One validator sees a block; another does not. If they vote from different views, they vote for different things, and the protocol makes no progress even when nobody is faulty. This is a liveness problem, not a safety problem.

View-merge removes it. Once per voting round, one chosen validator sends everyone its view. All validators then vote on the same merged view. That validator is the syncer. The syncer of a round is the available-chain proposer of the slot that starts it (full/height_filter_and_timeouts.tex:1643), so it is not a new role.

The mechanism has three instants (full/height_filter_and_timeouts.tex:2427-2437). Every validator freezes a snapshot at start(k) − Δ. The syncer sends its unfrozen store at start(k). Everyone votes on snapshot ∪ syncer store at start(k) + Δ. The freeze makes it work. A snapshot taken Δ early holds only messages that already reached the syncer. The merge then equals the syncer's store, and every honest validator gets the same view.

What was removed

The executable specification realised view-merge as message re-gossip rather than as a certificate. The round proposer replayed the round's retained aggregate objects onto the existing attestation topics:

validator.md:1108 — no longer in scope

"It re-gossips every valid support-round head and every conflicting copy it knows, including messages excluded from support, together with each named block and the ancestry needed to validate and project the messages. The proposal carries no TSQ root, quorum, signer list, vote bundle, or certificate."

Related text, by topic:

  • p2p-interface.md:121-129 — the relay pool, the bounded dependency queue, and the rule that overflow makes a round uncounted for TSQ liveness.
  • validator.md:261 — every round was a synchronisation round.
  • validator.md:1114 — the attestation pool had to retain concrete signed gossip objects, not Store data.
Why it mattered

One node would have published thousands of retained objects inside one slot, against a hard deadline, in the same slot it proposed a block. That is the only part of the design with no equivalent in Ethereum today. With it removed, the networking delta is small.

What to watch if it returns

  • The publisher pays D times the unique payload, because gossipsub pushes to every mesh peer before the duplicate check runs.
  • The publisher is also the block proposer for that slot. Prysm reorgs a late block.
  • Total-bytes measurements do not answer the real question. The nodes that need the replay are the ones whose peers already hold it and drop it. Measure per-node delivery of the messages that node was missing.
  • Prysm's attestation pool does not retain the signed wire object today. Any relay design needs that first.

Round-start blocks may still be larger

This part does not depend on the re-gossip. The round-start block carries the round's finality aggregates. An ordinary block carries one slot of votes.

Warning — the block holds exactly one round and no more

MaxAttestationsElectra is 8 (config/params/mainnet_config.go:177). One Electra attestation covers all 64 committees of one slot, because committee_bits is a Bitvector[64]. So a block holds 8 slots of votes, and a round of 8 slots fits exactly, with no headroom. Aggregates must have identical complete AttestationData, so votes naming different targets cannot merge. After asynchrony honest validators hold different targets, so the round needs more entries at the moment the block can hold fewer. Keep this on the list even with the re-gossip removed.

12 Clocks

A sub-round is one available-chain slot. So the gadget clock is the slot clock. You do not need a new ticker.

Practical rules for the mock:

  • Assign each validator to one slot of the 8-slot window. Copy the committee assignment logic and replace 32 with 8.
  • Make the finality-vote publish offset a flag. Slot start is the default, because the vote's fields freeze at the round start and do not need the slot's block. Publish aggregates at the existing aggregate deadline. config/params/mainnet_config.go:128-139 holds the deadlines as basis points.
  • Make m a flag. Traffic per round does not change with m, but the per-slot burst height falls as 1/m. m = 8 gives 4 times the attestation rate; m = 4 gives 8 times.
  • Drive everything from genesis time, as Prysm does, so every node fires together. Do not drive it from node start time.
  • Do not attach the gadget publish to NewSlot (beacon-chain/forkchoice/doubly-linked-tree/on_tick.go:32). That is the only slot-boundary hook Prysm has, and it runs under the fork choice lock.

15 Warnings

Read these before you start. Each one has caused a wrong measurement.

Warning 1 — a silent stub is worse than a wrong stub

A stub that returns IGNORE, or a topic that no node joins, shows almost zero traffic. This result looks correct and is not. Always compare the sender's published count with the receivers' accepted count. If the two counts do not agree within the expected duplicate factor, the path is broken.

Warning 2 — two nodes are not a network

Prysm's e2e harness runs 2 beacon nodes. Mesh degree D is 8. With 2 nodes, every gossipsub property you care about is absent. Use e2e to prove the code compiles and runs. Do not take a number from it.

Warning 3 — the specification is not finished

The candidate document lists seven properties as unproven. The syncer count, the syncer period, the sub-round count m, and the round length are all open. Any traffic figure you produce is conditional on the values you choose. Record them with every result.

Warning 4 — do not build a new message path

The finality gadget vote has the same network shape as an attestation. Both have one vote per validator per period. Both divide the validators across the period's slots. Both use BLS aggregation, subnets, aggregators, and block inclusion. Only the period differs: 8 slots in place of 32. If you start to design an aggregation scheme or a sub-round clock, stop. Read the ★ plan section again.

Warning 5 — the head rule is Goldfish, and it is not optional

Goldfish votes are ephemeral. A vote counts only in its own slot, and the gossip validator drops each message that is not for the current slot. A late vote is lost, not delayed. Vote timing is therefore a primary networking result, not a detail. If you build the available_attestation topic but let LMD-GHOST select the head, you have the messages without the protocol. The timing result then disappears.

Warning 6 — check what is already measured

Prysm exports per-topic gossip metrics already. Adding a second counter that counts something slightly different is a common source of contradictory results. Read beacon-chain/p2p/monitoring.go first.

Warning — the omissions bound what the result can claim

With this list, the simulation can answer three questions. Can the network carry the steady-state message load of decoupled consensus? At which validator count does it fail? What are the latency tails? It cannot answer questions about healing, TSQ convergence, incentives, or slashing. Put this list, and the run's flags, next to every published figure.
